# Deployment guide

Production uses Vercel for Next.js, Render for the Dockerized Spring Boot API,
and the existing Supabase PostgreSQL database. This guide targets `main`.

## Current deployment

| Component | Public URL |
|---|---|
| Frontend | https://student-management-system-henna-rho.vercel.app |
| Backend | https://student-management-api-pqza.onrender.com |
| Backend health | https://student-management-api-pqza.onrender.com/actuator/health |

The deployed application commit is `a274732`, merged through release PR #1.
Read-only live checks passed on 2026-10-16, and the production ADMIN dashboard
was shown loading records. See [release-checklist.md](release-checklist.md) for
the evidence and remaining manual verification.

## 1. Review and merge the release PR

Review the release preparation branch and the finished application changes it
includes. Let the GitHub Actions `Verify` workflow finish before merging into
`main`. It checks frontend lint, record tests, production build and HTTP auth
integration; backend authentication tests; executable JAR packaging; and a
Docker build. Tests use mock/in-memory data and need no database secrets.

The full Spring context test is excluded from the focused CI command because it
requires a real database and JWT configuration. The live checks below remain
necessary. Local Docker execution requires Docker Desktop or another Docker
engine; the hosted CI runner provides an engine for the image build.

## 2. Create the Vercel frontend project

1. Sign in to [Vercel](https://vercel.com/new) and import
   `AaqibAR/student-management-system` from GitHub.
2. Choose the intended account/project plan after reviewing its current terms.
3. Select **Next.js**, set **Root Directory** to `frontend`, and use Node 22.
   Keep Install Command `npm ci` and Build Command `npm run build`.
4. Use `main` as the Production Branch. Deploy, then copy the stable production
   HTTPS domain from the project Domains page, not a commit-specific preview URL.
5. The initial login screen can render before the backend is configured.
   Authentication will not work until steps 3 and 4 below are complete.

The `.nvmrc` and package `engines.node` keep the frontend on Node 22. Do not
set `output: export` or configure the app as a static website: its server pages,
session cookies, and API route handlers require the Next.js runtime.

## 3. Create the Render backend

The repository-root `render.yaml` defines one Docker web service on the Free
compute plan, using the existing Supabase database. It does not provision a
Render database. The default region is Singapore; review it before creation
if your Supabase project is elsewhere.

1. Sign in to [Render](https://dashboard.render.com/), choose **New → Blueprint**,
   connect this repository, and select `main` with `render.yaml`.
2. Check the displayed service name, region and **Free** plan before creating.
   The Blueprint sets `dockerfilePath: ./backend/Dockerfile` and
   `dockerContext: ./backend`. Do not set a separate root directory for this
   Blueprint setup.
3. Fill the requested environment variables using the table below. Enter
   secrets in Render's environment form, not in Git, this document, or chat.
4. Create the service, follow the build logs, then wait for the public health
   endpoint to return HTTP 200 with `status: UP`.
5. Copy the service's actual HTTPS origin for Vercel's `API_BASE_URL`.

| Render variable | Value |
|---|---|
| `DB_URL` | `jdbc:postgresql://YOUR_SESSION_POOLER_HOST:5432/postgres?sslmode=require` |
| `DB_USERNAME` | Exact Session pooler username, usually `postgres.YOUR_PROJECT_REF` |
| `DB_PASSWORD` | Supabase database password |
| `JWT_SECRET` | Generated by the Blueprint as a Base64 256-bit value; retain across restarts |
| `FRONTEND_URL` | Stable Vercel production HTTPS origin from step 2, with no trailing slash |
| `JAVA_TOOL_OPTIONS` | Already set in the Blueprint to `-XX:MaxRAMPercentage=65.0` |
| `PORT` | Supplied automatically by Render; no manual value needed |

Get the pooler host and username from Supabase **Connect → Session pooler**.
Keep password in its separate environment variable; do not embed it in the JDBC
URL. The session pooler uses port 5432 and supports the existing JDBC/Hikari
configuration. Copy the real host instead of constructing it from a region.

The existing database already has the application tables. Do not rerun the
initial CREATE TABLE script on it. For a genuinely new project only, run
`backend/sql/001_create_tables.sql` once before starting Spring Boot.

`/actuator/health` includes database health. A failed database connection/schema
validation can prevent startup or produce a failing health response. Fix the
first meaningful startup error rather than disabling health or validation.

The Docker build receives only Maven and main-source inputs. It packages an
executable JAR with JDK 21 and runs it with a JRE as UID 10001. Secrets are
runtime values, not Docker build arguments.

## 4. Connect and redeploy the frontend

In Vercel → project Settings → Environment Variables, set these for
**Production**:

| Vercel variable | Value |
|---|---|
| `API_BASE_URL` | Actual Render API HTTPS origin, e.g. `https://YOUR_SERVICE.onrender.com` |
| `APP_ORIGIN` | Exact stable frontend origin, e.g. `https://YOUR_PROJECT.vercel.app` |

Replace both examples with the actual assigned domains; no trailing slashes.
`API_BASE_URL` is server-only. No `NEXT_PUBLIC_` variable is required, and no
database password, Supabase service key, or JWT signing key belongs in Vercel.

The current production values are:

```dotenv
API_BASE_URL=https://student-management-api-pqza.onrender.com
APP_ORIGIN=https://student-management-system-henna-rho.vercel.app
```

Render's `FRONTEND_URL` uses that same frontend origin, without `/login` or a
trailing slash. These are public service addresses; database credentials and
the generated signing secret remain in Render's environment settings.

Redeploy the frontend after saving variables, then use the stable production
URL for testing. If you change domains, update `APP_ORIGIN` in Vercel and
`FRONTEND_URL` in Render, then redeploy the affected services.

Preview deployments have a different origin. Do not copy the production
`APP_ORIGIN` into a preview environment and expect its forms to pass the origin
check. Use the production domain for the final demo; configure any separate
preview environment deliberately with its own origin and test data.

## 5. Verify the live system

Start with read-only checks, substituting the real API origin:

```bash
curl --fail --show-error https://YOUR_SERVICE.onrender.com/actuator/health
curl --silent --output /dev/null --write-out '%{http_code}\n' https://YOUR_SERVICE.onrender.com/api/students
```

Expect health HTTP 200 and `UP`, then HTTP 401 for anonymous students. Opening
the backend root `/` or a protected endpoint without a token is not a test of
the frontend login page.

Open the frontend production URL. Complete the manual checks in
[release-checklist.md](release-checklist.md): USER and ADMIN permissions,
registration/login, persistence, validation/errors, mobile dialogs, logout,
expiry, and cross-tab behavior. Use disposable records.

If an ADMIN demo is needed, register a selected test account, promote that exact
email using the documented SQL in the root README, then log in again. Do not
publish the account's password or database credentials in documentation.

Record the final frontend URL, backend health URL, GitHub commit, and test results
in the checklist and root README only after successful verification.

## Free-tier startup behavior

Render's Free service sleeps after 15 minutes without inbound traffic and can
take about a minute to restart. This application's API requests time out after
15 seconds, so the first login after sleep can show a temporary-service error.
Before a demo, open the backend health URL, wait until it returns `UP`, then
retry the frontend. Data remains in Supabase across backend restarts.

For an always-ready service, evaluate an appropriate paid hosting plan yourself;
this repository's Blueprint selects Free.

## Troubleshooting

| Symptom | Check |
|---|---|
| Backend never becomes healthy | First startup error; DB host/username/password, Session pooler port 5432, existing `app` tables, valid Base64 JWT secret |
| No listening port detected | `PORT` is present; `server.port=${PORT:8080}`; bind address `0.0.0.0` |
| Frontend shows service unavailable | Backend health/wake-up state, Vercel `API_BASE_URL`, redeployment after env changes |
| A form returns 403 immediately | Exact `APP_ORIGIN`, stable production domain, no trailing slash, correct Vercel environment |
| USER cannot edit | Expected. Promote only the intended ADMIN account and log in again |
| Session ends after 15 minutes | Expected token lifetime; sign in again |
| Login works but browser session disappears | Use HTTPS; production cookie is Secure; check the selected frontend domain |
| CI fails on dependency resolution | Inspect the package/version or network error; do not change framework versions blindly |
| Docker build fails | Check the builder log, Maven wrapper download, and dependency resolution; local tests alone do not prove an image builds |
